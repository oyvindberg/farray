:::info[This page is an experiment, on purpose]

Nothing here is a JSON library, and none of it is on FArray's roadmap. It exists to answer exactly one
question: **is the fusion optimizer really about collections, or is it about pipelines?** So we
pointed it, *unchanged*, at raw JSON bytes — and it beat the JVM's best hand-tuned parser on
projection queries. Read it as a demonstration of how far the fusion machinery reaches, not as a
product.

:::

<p className="lede">
  The insight that makes it work: a JSON object is a <strong>product</strong> whose fields are{" "}
  <strong>columns</strong> — sourced from byte ranges instead of tuple slots. So the same optimizer
  from <Link to="/fusion/optimizer">the optimizer page</Link>, <em>unchanged</em>, becomes a projection-aware
  JSON parser. Wrap a byte buffer as a source, start a pipeline with <code>.stream</code>, and the
  macro reads your <code>.filter(…).map(…)</code> chain, works out which fields it actually touches,
  and emits one specialized per-record scanner over the raw <code>byte[]</code>. Dead fields are
  skipped at the byte level. A projected string is decoded only for survivors. A record whose filter
  fails is abandoned mid-scan. No per-record object is ever allocated.
</p>

## The setup — a record type and a source

Everything on this page starts from code you'd actually write, and there are only two pieces. The
first is a plain case class describing the record — **no codec, no `derives`, no annotations**. The
macro reads the field names and types straight off the case class; this is the 20-field record every
example below runs against:

<Snippet name="json-event" hideFull />

The second piece is a **source** — and this is the part of the page most worth internalizing:
`Json.ndjson` is not engine magic, it's *user-level code*. The fusion engine
([the sources page](./sources.mdx)) is a streaming consumer,
and its whole contract for byte data is one small trait, `ByteRecordSource`: "hand me the byte range
of the next complete record, in constant memory, and tell me when records run out." Six members:

<Snippet name="byte-record-source" hideFull />

The engine drives it with a two-level loop — `while nextChunk()` / `while nextRecord()` /
decode `buf[recordStart, recordEnd)` — done-gated at both levels so a downstream `find` or `take`
stops pulling, and wrapped in `try/finally close()`. Everything column-aware (which keys are live,
skip-versus-decode, predicate early-out) belongs to the *engine*; the source owns only framing and
I/O.

Which means the entire in-memory NDJSON adapter is this — one implementation of that trait, plus one
line (`def stream = new Fuse[T](this)`) to enter the pipeline. And the build enforces the claim: none
of the JSON code lives in farray. It sits in its own `example-json-decoder` module, downstream of the
engine, plugged in through a tiny discovery seam — exactly the position *your* decoder would occupy.
This is the real class, verbatim, and the shape of what you'd write to plug any record-framed format
— CSV, log lines, length-prefixed binary — into the same optimizer:

<Snippet name="ndjson-source" hideFull />

Three constructors package that up, one per place your bytes live — an `FArray` pipeline starts with
`.fuse`, a byte source starts with `.stream` (the different verb is deliberate: a call-site signal
that records are being consumed out of raw bytes):

<p className="fuse-cap">you write</p>
<Snippet name="fuse-src-jentry" hideFull />

The buffer variant scans in place — its `nextChunk()` returns `true` exactly once, as you just saw.
The file and `InputStream` variants swap in a framer whose `nextChunk()` reads the next block and
stitches records that straddle block boundaries, which is all it takes to make the same scanner run
in **constant memory** — O(one block + the largest record) — over a stream of any size, with the
source *owned*: closed on exhaustion, on short-circuit, and on exception alike.

## How that can possibly work

Your part is the whole list you just saw, so it bears spelling out:

<ul className="points">
  <li>Define a flat case class. It <em>is</em> the schema — no codec to derive, no given to import, nothing to register.</li>
  <li>Pick the constructor for where your bytes live; <code>.stream</code> into the pipeline.</li>
  <li>Write the <code>filter</code>/<code>map</code> chain you'd write over any collection, and end in a terminal.</li>
</ul>

The compiler's part happens when the terminal macro fires, and none of it is JSON-shaped until the
last step:

<ul className="points">
  <li>
    <strong>The source's static type picks the lowering.</strong> The macro walks the chain back to
    the expression the pipeline started from and checks its type: an <code>FArray</code> lowers to
    the indexed loops from the guide; a <code>ByteRecordSource</code> takes the record path. A
    compile-time type test — no runtime dispatch, no registry.
  </li>
  <li>
    <strong>The case class is read off the types.</strong> <code>.stream</code> on an{" "}
    <code>NdjsonSource[Event]</code> gives a <code>Fuse[Event]</code>, and the macro enumerates{" "}
    <code>Event</code>'s fields — names and kinds — straight from the type. That's the whole reason
    no codec exists: there is nothing a codec would know that the case class doesn't already say.
  </li>
  <li>
    <strong>The pipeline's lambdas decide what gets decoded.</strong> The macro computes the{" "}
    <em>live set</em> — the fields your filters, maps and aggregates actually touch. Each live field
    gets a byte-reader spliced in for its kind (<code>JsonScanner.readDoubleAt</code>, a lazy{" "}
    <code>(start, len)</code> slice for a String); every other field gets <code>skipValue</code>.
    The scanners shown below are exactly those splices, assembled per record.
  </li>
  <li>
    <strong>Then it rejoins the ordinary optimizer.</strong> The decoded fields re-enter the engine
    as columns — the same columns a tuple-returning <code>map</code> produces — so dead-column
    elimination and compute-for-survivors work over byte ranges for free. The JSON-specific part is
    one pluggable decoder living in its own module (<code>example-json-decoder</code>), discovered on
    the compile classpath when the macro expands; a columnar or protobuf decoder would plug into the
    same seam without the engine changing.
  </li>
</ul>

And the failure mode is the compiler, not the runtime: a field type outside{" "}
<code>Int</code>/<code>Long</code>/<code>Double</code>/<code>String</code>, or a stage the record
path doesn't support yet, is an error at the call site.

## The pipeline is the one you already know

`.stream` hands you the same `Fuse[Event]` you know from [the user guide](./index.mdx) — you already
know what `filter` and `map` mean, and they mean exactly that here. Most of the surface simply works
over a JSON source. Concretely, in the current experiment:

<ul className="points">
  <li>
    <strong>Stages:</strong> <code>filter</code> and <code>map</code> (and for-comprehension guards
    via <code>withFilter</code>) — which covers the projection-and-predicate queries this page is
    about.
  </li>
  <li>
    <strong>Terminals — the field-reading set:</strong> <code>sum</code> · <code>foldLeft</code> /{" "}
    <code>fold</code> · <code>reduce</code> · <code>count</code> · <code>foreach</code> ·{" "}
    <code>toList</code> · <code>find</code> · <code>exists</code> · <code>forall</code> ·{" "}
    <code>indexWhere</code> · the multi-aggregates <code>agg</code> / <code>aggTo</code> — plus
    everything the guide showed desugaring onto these (<code>toVector</code>/<code>toSet</code>/
    <code>mkString</code> via <code>foreach</code>; <code>min</code>/<code>max</code>/
    <code>minBy</code>/<code>maxBy</code> via the reduce aggregates; <code>isEmpty</code>/
    <code>nonEmpty</code>/<code>contains</code> via <code>exists</code>).
  </li>
  <li>
    <strong>Not yet:</strong> nested objects/arrays (records are flat{" "}
    <code>Int</code>/<code>Long</code>/<code>Double</code>/<code>String</code> fields, compact
    one-record-per-line NDJSON), and the <code>zip</code>/<code>flatMap</code>/<code>collect</code>/
    <code>takeWhile</code>/<code>distinct</code> stages — each is a clear <em>compile error</em> over
    a JSON source, never a silent fallback to something slower.
  </li>
</ul>

## The benchmark

The dataset is NDJSON — one JSON object per line — of **10 000 records**, **~3.2 MB**, each a
**20-field** object (~334 bytes: a realistic mix of longs, ints, doubles, and strings). Every query
touches just **1–2 of those 20 fields** — the projection case where pushdown pays. Throughput is
ops/s over the whole 10 000-record buffer; allocation is bytes per buffer-op (÷10 000 ≈ bytes per
record). Every parser runs the same query: the fuse row is the generated scanner, and each rival row
is that library's best idiom for "read a couple of fields per line."

## Projection pushdown — read 1 field of 20

The pipeline reads only `amount`. Every other field is a dead column with no slot: the generated
scanner hands it to `skipValue`, which advances past its bytes without decoding or allocating
anything. A 20-field record costs one number-parse and nineteen byte-skips. No `Event` is built; the
fold runs into a `var`.

## Lazy decode — a String built only for survivors

`category` gets a slot, but a string slot is just `(start, len)` into the buffer — not a decoded
String. `amount` decodes, because the filter needs it; `category` stays a byte slice and becomes a
real `String` only inside the survivor `if`. Rejected rows never allocate a String. It's the same
compute-for-survivors sink from [the optimizer page](./optimizer.mdx), now operating on bytes.

<JsonEx
  src="fuse-src-jcat" gen="fuse-json-cat"
  rival="rival-cat" rivalLabel="jsoniter-scala, narrow codec (only the read fields; the rest skipped)"
/>

## Discard-DCE — count never decodes the projection

`count` ignores the element, so `map(_.category)` is a dead value. The optimizer captures the slice
but never turns it into a String — zero String allocations across the whole run. The same holds for
`isEmpty`/`nonEmpty`, and for `map(expensive).count`, where `expensive` never runs at all. Dead-column
elimination, reaching all the way to the terminal.

<JsonEx src="fuse-src-jcount" gen="fuse-json-count" bench={COUNT_BENCH} />

## Predicate-fail early-out — abandon a record mid-scan

The filter field is decoded *during* the scan; the instant it's known, the predicate runs inline, and
on failure the record is abandoned right there — the scanner never even looks for the later projected
field. Here `key` comes first, `payload` (a long string) comes last, and 90% of records are rejected:
each rejected record costs only "scan to `key`, compare, stop." On fat, selective queries this is the
biggest win of all.

<JsonEx src="fuse-src-jwide" gen="fuse-json-wide" bench={WIDE_BENCH} />

## Multi-aggregate — three aggregates, one pass, into a case class

Sum the amount, count the rows, and take the peak score of the active events. The aggregates are the
guide's `Agg` values (`Agg.sum`, `Agg.count`, `Agg.max1`, …), and the result lands in your own case
class:

<Snippet name="json-stats" hideFull />

`aggTo` runs all three in a single fused scan, carrying one unboxed accumulator each. The columns the aggregates read are
merged automatically: `amount`, `status`, and `score` are scanned — 3 of 20 fields, each exactly once
— and `count` reads nothing extra. The result is a case class, not a tuple; no `Event` is ever built,
and the sum and max compile to `dadd`/`dcmp`, not a boxing `Numeric`/`Ordering`.
