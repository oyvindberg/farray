## Why that number is possible

A JSON object is a product whose fields are columns, sourced from byte ranges instead of
tuple slots. That makes every trick from <Link to="/fusion/optimizer">the optimizer page</Link> apply
verbatim, at the byte level: the macro (the code generator that runs inside the compiler, behind
the terminal call) computes the *live set* (the fields your filters, maps and
aggregates touch) and emits a per-record scanner where every live field gets a typed byte
reader and every other field is skipped without being decoded. A 20-field record queried on one
field costs one number-parse and nineteen byte-skips. No `Event` object is ever built.

The queries on this page run against a 10 000-record, ~3.2 MB NDJSON buffer of that 20-field
`Event`: realistic field mix, every query touching 1–2 fields, the projection case where pushdown pays.
Throughput is ops/s over the whole buffer (÷10 000 ≈ per record); every rival runs that library's
best idiom for the same query.

## The whole integration, one file

Before the demos, the part a library author should read closely. This is the whole plug-in,
verbatim: the shape, the typeclass instance (an interface implementation the compiler selects by
type, like a ServiceLoader resolved at compile time), and the hook.

<Snippet name="json-integration" hideFull />

Unpacking it against <Link to="/fusion/terminals">the lowerings page</Link>: `Ndjson` is the source
shape, and the given (Scala's keyword for publishing such a compiler-resolved instance) in its
companion puts `JsonLowering`'s terminals on every `Fuse[A, Ndjson]`. `StandardTerminals[Ndjson]`
is where the terminal *methods* come from: mixing it in is what makes `.sum`, `.find`,
`.groupAdjacentReduceBy` and the rest exist on these pipelines at all (and what makes `.run` not
compile; element materialization isn't in the mixin list). Every one of those methods is sugar
that funnels into the single abstract `lower` you see in the file.

So the hook is the entire integration surface, and it does exactly one thing. `lower` is an inline
macro; its `impl` calls `FuseMacro.lower(self, t, JsonDecode)`, handing the engine three values at
compile time: the pipeline's own syntax tree (`self`), the reified terminal (`t`), and the decoder
object. No registry, no reflection, no runtime handshake; the decoder rides along as an ordinary
method argument inside the compiler.

The other two pieces are just as inspectable. The **source** contract is six methods, "hand me the
byte range of the next complete record, in constant memory":

<Snippet name="byte-record-source" hideFull />

…and the in-memory NDJSON source is one small implementation of it, plus `def stream` to enter the
pipeline:

<Snippet name="ndjson-source" hideFull />

The **decoder** (`JsonDecode.scala`) is the format-specific work, and its contract with the engine
is one conversation, at macro-expansion time. The engine calls the decoder once per pipeline with a
request carrying: the record's case-class type, the runtime byte source, the pipeline's `map` and
`filter` lambdas plus the terminal's element readers (the decoder walks these to compute the *live
set*, which fields anything downstream actually reads), a short-circuit flag for `take`/`find`, and
a `continue` callback the engine owns. The decoder answers with one column per record field, in
declaration order: each column is a read thunk that emits the byte-level code for that field, or a
skip plus default constant if the field is dead. That's all it answers; the engine takes the
columns and does the rest: memoizing String reads so a field decodes at most once, placing
predicates for the mid-record early-out, assembling whatever the terminal needs, and emitting the
loop. That split of labor is why the decoder stays small, and why a CSV or length-prefixed-binary
decoder would be the same shape: implement the framing, implement the per-field reads, publish a
given.

Three entry points, one per place your bytes live; the file and stream variants run in constant
memory (one block + the largest record), with the source closed on every exit path:

## The demos

Each isolates one optimizer behavior over bytes, with the generated scanner and, where a fair rival
exists, that library's best idiom for the same query.

### Projection pushdown: read 1 field of 20

The pipeline reads only `amount`. Every other field is a dead column with no slot: the scanner hands
it to `skipValue`, which advances past its bytes without decoding or allocating anything. No `Event`
is built; the fold runs into a `var`:

/>

### Lazy decode: a String built only for survivors

`category` gets a slot, but a string slot is just `(start, len)` into the buffer. `amount` decodes
because the filter needs it; `category` becomes a real `String` only inside the survivor branch.
Rejected rows never allocate one: the compute-for-survivors sink, operating on bytes:

<JsonEx
  src="fuse-src-jcat" gen="fuse-json-cat"
  rival="rival-cat" rivalLabel="jsoniter-scala, narrow codec (only the read fields; the rest skipped)"
/>

### Discard-DCE: count never decodes the projection

`count` ignores the element, so `map(_.category)` is a dead value: the slice is captured, the
`String` never built, and zero String allocations occur across the run. Dead-column elimination
reaches all the way to the terminal:

<JsonEx src="fuse-src-jcount" gen="fuse-json-count" bench={COUNT_BENCH} />

### Predicate-fail early-out: abandon a record mid-scan

The filter field is decoded *during* the scan, the predicate runs as soon as it's known, and a
failing record is abandoned there; the scanner never looks for the later projected
field. Here `key` comes first, `payload` (a long string) last, and 90% of records fail: each
rejected record costs "scan to `key`, compare, stop":

<JsonEx src="fuse-src-jwide" gen="fuse-json-wide" bench={WIDE_BENCH} />

## The pipeline surface over JSON

`.stream` hands you the same pipeline type as everywhere else, narrowed to what the record path
supports: `filter`/`map`/`withFilter` stages; the aggregation, search, group-reduce and plan terminal
families (`sum`, `foldLeft`, `count`, `find`, `exists`, `toList`, `agg`/`aggTo`, `groupSum`,
`topNBy`, …). Records are flat `Int`/`Long`/`Double`/`String` case classes over one-line NDJSON.
Everything outside that (nested objects, `zip`, `flatMap`, `collect`) is a compile error at the
call site, and an unsupported *terminal* is not a member. No silent fallback exists.
