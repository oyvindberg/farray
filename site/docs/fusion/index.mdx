## The problem, stated the way a profiler states it

Every JVM collections pipeline (Scala collections, Java Streams, the wrapper libraries) pays some
mix of three taxes:

<ul className="points">
  <li>
    <strong>Intermediates.</strong> Eager stages each allocate a collection whose only purpose is to
    be consumed and thrown away by the next stage. Three stages over 100k elements is two garbage
    arrays, and on primitives often two garbage arrays <em>of boxes</em>.
  </li>
  <li>
    <strong>The lambda tax.</strong> Lazy views and streams fix the intermediates by threading
    elements through stored <code>Function1</code>s (Scala's function-object interface, like{" "}
    <code>java.util.function.Function</code>): an interface call per element per stage. One call
    site serving ≥3 lambda classes goes megamorphic and stops devirtualizing; on primitives, every
    crossing boxes. <code>java.util.stream</code> is the Java face of the same trade: it fuses your
    pipeline, but at <em>runtime</em>, by pushing each element through a chain of virtual{" "}
    <code>Sink.accept</code> calls, one per stage, with the same megamorphic fate in real code, and
    boxed outside the three primitive specializations. <code>.fuse</code> removes that chain at{" "}
    <em>compile</em> time, so the runtime sees one loop.
  </li>
  <li>
    <strong>The JIT gamble.</strong> Escape analysis and inlining can sometimes claw both back, until
    the enclosing method grows past an inlining budget, a call site gets polluted, or one trailing
    virtual call silently turns escape analysis off. We measured that cliff at{" "}
    <Link to="/operations/flatmap">35× on this very library</Link> before designing around it. Speed
    that depends on JIT heuristics is not dependable.
  </li>
</ul>

The fast code is known: a `while` loop over the backing array with the logic written inline.
Writing it by hand trades away every abstraction collections provide.

## The move: compile the pipeline

Fusion makes the *compiler* write that loop. The stages you chain are inert markers; the **terminal**
call at the end is a macro (code that runs inside the compiler and rewrites the typed syntax tree;
javac has no counterpart at expression level, annotation processors only see declarations) that
reads the entire chain off the typed syntax tree and emits the hand-written loop, with your lambdas
spliced into the body, element types resolved, nothing boxed, and nothing allocated between stages:

<FuseEx src="fuse-src-oneloop" gen="fuse-opt-oneloop" />

The output contains no `Function1`: `_ + 1` became the add instruction in the loop body. The filter
is an `if` wrapping everything downstream. There is one output array, sized once, and no trace of
the pipeline objects themselves: the source lands in `src0` as a bare reference.

Because this happens at *compile* time, none of it is a JIT bet. The specialization is in the
bytecode: monomorphic, unboxed, allocation-free before the VM has compiled a single method. That is
why a fused pipeline leads even measured cold, and why the lead persists when the enclosing method
grows or a call site gets shared. The taxes are avoided in the emitted bytecode rather than
optimized away at runtime.

## The machine, in five concepts

Everything in this section builds from five ideas, each with its own page, each depending only on
the ones before it:

<ul className="points">
  <li>
    <strong><Link to="/fusion/sources">Sources</Link></strong>: where elements come from. An
    in-memory <code>FArray</code>, a chunked stream pulled in constant memory, or raw bytes framed
    into records. A pipeline's source shape is part of its type.
  </li>
  <li>
    <strong><Link to="/fusion/stages">Stages</Link></strong>: the pipeline vocabulary.{" "}
    <code>map</code>, <code>filter</code>, <code>collect</code>, <code>zip</code>, and the
    clustered-data family are markers that cost nothing and compile to nothing but their spliced
    bodies.
  </li>
  <li>
    <strong><Link to="/fusion/terminals">Terminals & lowerings</Link></strong>: the call that ends
    the chain <em>is</em> the compiler invocation. Which terminals a pipeline has is decided per
    source shape by a typeclass (an interface implementation the compiler selects by type, like a
    ServiceLoader resolved at compile time), which is what makes the engine extensible.
  </li>
  <li>
    <strong><Link to="/fusion/optimizer">The optimizer</Link></strong>: the shared brain. Products
    are decomposed into columns, dead columns are never computed, and expensive columns are computed
    only for survivors.
  </li>
  <li>
    <strong><Link to="/fusion/json">The integration surface</Link></strong>: a JSON decoder plugged
    in as a typeclass instance that beats the JVM's best hand-tuned parser, showing the engine is
    not collection-specific. <Link to="/fusion/farray">Using it with FArray</Link> and{" "}
    <Link to="/fusion/benchmarks">the benchmarks</Link> close the section.
  </li>
</ul>

## The contract

:::warning The purity rule is load-bearing
Fused stage lambdas must be pure. The optimizer reorders, sinks and deletes computations on that
assumption, and nothing checks it: a logger or counter inside a fused stage compiles fine and is a
semantic bug. [Sharp edges](../semantics.mdx) spells out what can happen.
:::

Four rules:

<ul className="points">
  <li>
    <strong>Stage lambdas are assumed pure.</strong> A fused pipeline is lazy and short-circuiting:
    under <code>take</code>, <code>find</code>, <code>exists</code> a stage function may run{" "}
    <em>fewer</em> times than in the strict <code>List</code> version, and a column read only after a
    filter is computed only for elements that pass. Pure functions produce identical results;
    side-effecting ones can observe the difference.
  </li>
  <li>
    <strong>Element kinds are checked at compile time.</strong> <code>Int</code>/<code>Long</code>/
    <code>Double</code> or a reference type; a primitive pipeline widened to <code>Any</code> is a
    compile error, never a silent deoptimization.
  </li>
  <li>
    <strong>The chain must be written out at the call site.</strong> It's read off the syntax tree,
    not built at runtime; a pipeline assembled dynamically is a job for the eager ops.
  </li>
  <li>
    <strong>Unsupported means "does not compile".</strong> A terminal a source shape doesn't support
    is not a member of the pipeline's type; a stage the record path can't fuse is an error naming the
    stage. There is no fallback path that silently runs slow.
  </li>
</ul>
