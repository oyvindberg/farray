## One loop, from wherever the data lives

Every eager FArray operation is a compiled-once loop — excellent alone, but chain three of them and
you build two intermediate arrays whose only purpose is to be thrown away. `.fuse` is the other gear.
You write the same chain, and the **terminal** call — a macro — reads the whole thing off the typed
syntax tree and emits *one* `while` loop with your lambdas spliced into the body: no intermediate
collections, no `Function1`s, nothing boxed. The **stages** in between are free markers; a chain with
no terminal does nothing and costs nothing.

The second thing to know reframes the first: the engine is not an array trick, it's a **streaming
consumer that abstracts over sources**. An in-memory `FArray` is just the simplest source — the whole
collection arrives as one chunk, and `run` hands you an `FArray` back, so fusion slots invisibly into
eager FArray code. But the same pipeline compiles over *streaming* sources: `Source.fromIterator`,
`Source.unfold`, `Source.iterate` pull unboxed chunks on demand, and `Json.ndjson[Rec](bytes)` +
`.stream` decodes records straight out of raw bytes. Streaming runs in **constant memory** — the loop
holds one chunk (~4096 elements), not the data, so a gigabyte file needs kilobytes of heap — and the
driver wraps everything in `try/finally close()`, so a file or socket is released on exhaustion, on
short-circuit, and on exception alike. The full story is on [the sources page](./sources.mdx); the
point here is that everything below works the same over all of them.

Here's the shape of it, on the example worth staring at first — `collect`, because it shows the part
no other collection library on the JVM can do: **unboxed**:

<FuseEx src="fuse-src-guide-collect" gen="fuse-guide-collect" />

Look at what became of the partial function. In the standard library, `collect` allocates a
`PartialFunction[Int, Int]` object and runs every element through `applyOrElse` — a generic method,
so every `Int` boxes to `Integer` on the way in and out, twice per element. Here there is no
`PartialFunction` at all: the `case x if x % 2 == 0 => x * 2` was spliced **into the loop body** as a
plain pattern match on an unboxed `Int` — the guard is the branch, the result is stored straight into
the output `int[]`. A "partial function" that compiles to an `if` is exactly what you meant when you
wrote it.

## The rules of the game

Four things to know before you lean on it — this is the entire contract:

<ul className="points">
  <li>
    <strong>Stage lambdas are assumed pure.</strong> A fused pipeline is lazy and short-circuiting:
    under <code>take</code>, <code>find</code>, <code>exists</code>, <code>head</code> a stage function
    may run <em>fewer</em> times than in the strict <code>List</code> version, and
    compute-for-survivors means a column read only after a <code>filter</code> is computed only for
    elements that pass. For pure functions the result is identical; a side-effecting lambda can observe
    the difference.
  </li>
  <li>
    <strong>Element kinds are checked at compile time.</strong> <code>Int</code>/<code>Long</code>/
    <code>Double</code> or a reference type. A primitive-backed FArray widened to <code>Any</code> is a
    compile <em>error</em> — never a silent miscompile.
  </li>
  <li>
    <strong>Stages are markers; the terminal is the macro.</strong> The chain must be written out at
    the call site — it's read off the typed syntax tree, not built at runtime.
  </li>
  <li>
    <strong>Adjacent stages are rewritten algebraically.</strong> <code>take(n).take(m)</code>{" "}
    collapses to one clamped limit, <code>drop(n).drop(m)</code> to one counter, and a{" "}
    <code>take</code> slides left past a <code>map</code> to meet another — you can compose freely
    without leaving loop machinery behind.
  </li>
</ul>

## The operations that only exist here

The rest of the page is the part worth your time: operations the standard collections don't have,
each doing in one fused pass what normally takes several — or takes allocation you can't avoid. The
examples share one record, straight from the snapshot tests that generate every lowering below — a
trade log, already ordered (and therefore clustered) by day:

<Snippet name="guide-trade" hideFull />

### Several answers from one pass — agg and aggTo

The classic end-of-pipeline problem: you want the sum *and* the count *and* the max, and your options
are three traversals or a hand-rolled fold over a tuple (which boxes). `agg` runs up to four
aggregates in one pass, each riding its own unboxed accumulator — `Agg.sum(f)`, `Agg.count`,
`Agg.min`/`max`/`min1`/`max1`, `Agg.avg`, `Agg.fold(z)(op)`, `Agg.reduce`, `Agg.minBy`/`maxBy`,
`Agg.topNBy` — and the loop body is just N statements:

<FuseEx src="fuse-src-guide-agg" gen="fuse-guide-agg" />

`aggTo` is the same machine with a better landing: pass a constructor and the results arrive as your
own type instead of a tuple — note the last line of the lowering is a plain `Summary.apply(total, n,
top)`, not a `Tuple3` you then have to unpack:

<FuseEx src="fuse-src-guide-aggto" gen="fuse-guide-aggto" />

### Group-reduce without the boxing — groupReduceBy, groupSum, groupCount

`groupBy` builds a `Map[K, List[A]]` — fine when you want the rows, pure overhead when you only want
an aggregate per key. `groupReduceBy(key)(value)(op)` folds each group *as elements stream past*,
into a primitive-keyed open-addressing table: an `Int` key and an `Int`/`Long`/`Double` accumulator
stay unboxed in the hot loop, and boxing happens exactly once per **key**, at the final O(#keys)
materialization into the `Map` you asked for. `groupSum(key)(value)` and `groupCount(key)` are the
spellings you'll actually reach for:

<FuseEx src="fuse-src-guide-groupsum" gen="fuse-guide-groupsum" />

### Clustered data, streamed — the adjacent family

A shape the standard library has no answer for at all: data that arrives *already clustered by key* —
a time-ordered trade log grouped by day, an access log grouped by request id, any sorted export. A
hash-`groupBy` would buffer the entire dataset to rediscover an order it already had. The adjacent
operations exploit the order instead — and because they're **stages**, they compose with everything
downstream and short-circuit; over a streaming source they process a file of any size in constant
memory.

**`foldAdjacentBy(key)(seed)(combine)`** emits one `(key, acc)` pair per maximal run of equal keys.
O(1) memory — the whole state is the current key and one accumulator. Per-day totals over the trade
log, and the lowering to read it by: the emit happens on key *change*, with the last run flushed
after the loop:

<FuseEx src="fuse-src-guide-foldadj" gen="fuse-guide-foldadj" />

**`groupAdjacentBy(key)`** is for when you need the run's *rows*, not an aggregate: each run becomes
its own `FArray[A]`, buffering one run at a time — O(largest run), never O(N). Downstream stages see
a stream of groups, so a `take` stops the source after enough *runs*:

<FuseEx src="fuse-src-guide-groupadj" gen="fuse-guide-groupadj" />

**`groupAdjacentReduceBy(key)(prep)(agg)`** is nested fusion, and the headline of the family: run a
*fused sub-pipeline* over each run's rows and emit `(key, result)` per run. `prep` is ordinary stages
over the group, `agg` its aggregate — and because the aggregate here is a fold, the run's rows are
**never materialized**: look at the lowering — the inner `map`/`filter` runs inline as each row
streams past, the accumulator resets on key change, and no per-group collection ever exists:

<FuseEx src="fuse-src-guide-nested" gen="fuse-guide-nested" />

One honest precondition for all three: "clustered by key" is *your* declaration. On unordered input
the result is per-run, not per-key — documented, not detected.

### The n best, without the sort — topN, bottomN, topNBy, bottomNBy

"Top ten by score" usually costs a full O(N log N) sort — or a `sortBy(…).take(10)` that materializes
and sorts everything to keep ten. `topNBy(n)(key)` keeps a bounded size-*n* heap inside the one pass:
O(N log n) time, O(n) memory, results best-first, and it composes with every stage upstream:
