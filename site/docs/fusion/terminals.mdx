Four of them deserve their lowerings shown, because they do things the standard library can't.

**Search terminals genuinely stop the machine.** `find` plants a done-flag that every loop level
carries — across sources and `flatMap` nesting alike — so the traversal ends the instant the answer
exists:

<FuseEx src="fuse-src-guide-find" gen="fuse-guide-find" />

**`agg` answers several questions in one pass.** The classic end-of-pipeline dilemma — sum *and*
count *and* max — is normally three traversals or a boxing tuple-fold. Here each aggregate rides its
own unboxed accumulator and the loop body is just N statements:

<FuseEx src="fuse-src-guide-agg" gen="fuse-guide-agg" />

**`aggTo` lands the answers in your own type.** Same machine, but the last line of the lowering is
`Summary.apply(total, n, top)` instead of a tuple you unpack:

<FuseEx src="fuse-src-guide-aggto" gen="fuse-guide-aggto" />

**`groupSum` folds groups without boxing.** `groupBy` builds a `Map[K, List[A]]` — pure overhead when
you only wanted an aggregate per key. `groupReduceBy` (and its `groupSum`/`groupCount` spellings)
folds each group *as elements stream past* into a primitive-keyed open-addressing table: `Int` keys
and `Int`/`Long`/`Double` accumulators stay unboxed in the hot loop, and boxing happens exactly once
per **key**, at the final O(#keys) materialization:

<FuseEx src="fuse-src-guide-groupsum" gen="fuse-guide-groupsum" />

And the ranking family, because "top ten by score" should not cost a sort: `topNBy(n)(key)` keeps a
bounded size-*n* heap inside the pass — O(N log n) time, O(n) memory, best-first:

## Lowerings: where terminals come from

Here's the part of the design a library author should care about. None of the methods above is
defined on the pipeline class. `Fuse[A, S]` carries only the stage markers; `S` is the pipeline's
**source shape** (<Link to="/fusion/sources">previous page</Link>), and the terminals are inline
extension methods provided by the shape's `FuseLowering[S]` **given** — published in the shape's
companion object, so it rides the implicit scope of every `Fuse[A, S]` with no imports at the use
site.

Three consequences, in increasing order of importance:

<ul className="points">
  <li>
    <strong>Scope lives in the types.</strong> A shape mixes in the terminal families it supports —
    the capability traits <code>AggTerminals</code>, <code>SearchTerminals</code>,{" "}
    <code>GroupTerminals</code>, <code>PlanTerminals</code>, <code>MaterializeTerminals</code>{" "}
    (bundled as <code>StandardTerminals</code>). A terminal a shape doesn't mix in is <em>not a
    member</em> of its pipelines. Not a runtime error, not a slow fallback: it doesn't compile.
  </li>
  <li>
    <strong>The syntax is written once.</strong> Those traits contain every method above, each a
    one-liner that reifies the call into a typed <code>Terminal[A, R]</code> marker —{" "}
    <code>Terminal.find(p): Terminal[A, Option[A]]</code> — and hands it to the one abstract hook a
    lowering implements.
  </li>
  <li>
    <strong>The hook is the whole integration.</strong> A lowering module implements a single{" "}
    <code>inline def lower(self, t)</code> whose macro forwards pipeline + terminal to the engine —
    together with the module's decoder, as an ordinary method argument at compile time. No registry,
    no reflection, no service files. The NDJSON decoder's entire hook is five lines; you'll read them
    on <Link to="/fusion/json">the JSON page</Link>.
  </li>
</ul>

The native shape (`FuseNative` — in-memory arrays and chunk streams) mixes in everything. The JSON
shape takes `StandardTerminals` and skips `MaterializeTerminals` — which is exactly why
`Json.ndjson[T](bytes).stream.run` is a compile error while `.sum` is a byte-level scanner: the
difference between the two shapes is spelled where a reader can see it, in the mixin list.
