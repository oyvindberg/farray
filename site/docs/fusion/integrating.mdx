<p className="lede">
  To integrate a new data source you need the engine's real shape, which the user-facing pages
  never had to state. The fusion engine is not a collections library that learned about bytes; it
  is an assembler that builds one loop out of three parts. A <strong>driver</strong> owns
  iteration: who advances, when to stop. <strong>Columns</strong> are how the parts of one element
  get read: an array index, or twenty byte-level field scans. A <strong>terminal</strong> owns the
  accumulators. Stages and the optimizer live entirely in the column layer and never learn where
  columns come from. Integrating a format means providing a driver and a way to make columns; the
  optimizer is not yours to build, and it works on day one.
</p>

Read the bottom of each. They end in the same code: a `val keep = <predicate>` and a guarded
accumulation. That part came from the shared machinery. Everything above it is the answer to one
question, "how do I read this element's columns": the array world answers with `a(i)`; the JSON
world answers with a key-matching scan that decodes `amount` (`readDoubleAt`) and walks past every
other field without decoding it (`skipValue`), abandoning the record scan the moment the last live
field is captured (`if (seen) open = false`). Different worlds above the line, the same optimizer
below it.

## The column model, in one paragraph

Inside the engine a value in flight is not an object; it is a set of columns. A scalar column is a
deferred read that binds to a `val` on first use and is reused after (so a column read only inside
a filter's guard is computed only for survivors). A product is its columns plus a rebuild function
that fires only if someone uses the value whole. `map` and `filter` transform and guard columns;
`.map(_._2)` plucks column two and the others never fire; a column nothing reads is never emitted
at all. Dead-code elimination, compute-for-survivors and decode-once memoization are all corollaries
of this one representation, which is why the <Link to="/fusion/optimizer">optimizer page</Link>
never mentions data formats.

The seam is now easy to state: **to the engine, a JSON record is a tuple.** When the decoder hands
over its per-field columns, the engine wraps them in exactly the product-of-columns it would have
built for a tuple literal in a `map` lambda, and from that line on there is no byte-specific code
path in the machine. String columns get the standard memoizer, which is where "a field decodes at
most once, and only for survivors" comes from: it is the ordinary in-memory behavior, inherited.

## The familiar half: chunks and records

The driver for byte sources rests on a distinction worth being precise about, because the memory
story hangs on it. A byte source deals in two units:

- **A chunk is a unit of memory.** The source holds exactly one block of bytes at a time: `buf`,
  advanced by `nextChunk()`. A file source reads block after block; an in-memory source answers
  `nextChunk()` with `true` exactly once. Nothing upstream ever demands two blocks at once.
- **A record is a unit of meaning.** Within the current chunk, `nextRecord()` frames the next
  complete record as a range, `recordStart` until `recordEnd`, no copy and no allocation; the
  generated scanner reads fields straight out of `buf` between those bounds.

The engine emits exactly the nesting you'd guess, with `close()` in a `finally` that fires on
exhaustion, short-circuit and exception alike:

```scala
try
  while (source.nextChunk() && notDone)     // memory: one block resident
    while (source.nextRecord() && notDone)  // meaning: one complete frame
      scan(source.buf, source.recordStart, source.recordEnd)
finally source.close()
```

The two units don't line up: records do not respect block boundaries. That misalignment is modeled
as a small ADT, and making "unfinished record" a first-class value instead of an offset somebody
has to remember is what keeps the boundary logic in exactly one place:

## Where terminals come from

None of the terminal methods is defined on the pipeline class. `Fuse[A, S]` carries only the stage
markers; `S` is the pipeline's source shape, and the terminals are inline extension methods
provided by the shape's `FuseLowering[S]` given, published in the shape's companion object, so it
rides the implicit scope of every `Fuse[A, S]` with no imports at the use site.

Three consequences:

The last four lines exist to solve one problem: the engine and your format have never met.
`FuseMacro` lives in farray and can compile any pipeline into a loop, but it has no idea how to
read your bytes; your module owns the decoder, but has no loop compiler. The hook is the meeting
point, and it happens inside the compiler, because that is where the loop gets generated.

What actually happens when a user writes `pipeline.sum`: the terminal method reifies the call and
lands in `lower` during compilation. Three things go across to the engine: the pipeline as the user
wrote it, the terminal that ended it, and `JsonDecode`, your decoder. The engine builds the scanner
loop and returns it, and that loop is compiled into the user's program in place of the `.sum` call.
By runtime these four lines have no existence; only the loop they brokered remains.

Why it takes two declarations and this exact punctuation: that is Scala 3's required ritual for
crossing from ordinary code into compiler-executed code and back. It is not a place where your
integration does anything. Copy the four lines verbatim; the only token that is yours is the
decoder's name.

## The decoder: answering the column question

With the model in hand, the decoder's job stops being abstract. The engine asks it, once per
pipeline, at compile time: *"here is the record type, here is every lambda in the pipeline and the
terminal's readers; produce this record's columns."* Concretely the decoder:

1. **Computes the live set.** It walks the lambdas' syntax trees collecting field paths: a pipeline
   of `.filter(_.amount > 150).map(_.category)` touches `amount` and `category`, so of a 20-field
   record those two are live and eighteen are dead. (A lambda that uses the record *whole* makes
   every field live; so do the terminals that keep whole elements, see the boundaries below.)
2. **Answers with one column per field, in declaration order.** A live numeric field's column is a
   read of the `var` its scanner fills (`readDoubleAt` in the snapshot above). A live String
   field's column stores slice bounds during the scan and emits the actual `new String` only when
   read, which, combined with the engine's memoizer, means: decoded at most once, and only for
   records that survive the filter. A dead field's column is a typed default constant that no one
   will read, and its bytes are `skipValue`d.
3. **Optionally hands the engine a leading-filter early-out**: if the pipeline starts with plain
   `filter`s whose fields appear before projection-only fields in the record, the emitted scanner
   evaluates the predicate mid-record and abandons the rest of the scan on failure. The filter is
   still re-checked downstream; the early-out is an optimization, never the correctness path.

Everything else in the emitted code, the memoization, the predicate placement, the accumulators,
the loop, is the engine's, shared with the in-memory world. That split is why the NDJSON decoder is
one file, and why a CSV or length-prefixed-binary decoder would be the same shape: implement the
framing, implement the per-field reads, publish a given.

The decoder also renders its decisions as a plan string
(`JsonPlan(record=Event, live=[amount], decoded=[amount], earlyOut=…, rebuildsRecord=false)`), and
the test suite asserts on plans as well as on the golden lowerings, so "which fields does this
query touch" is pinned by tests, not by faith.

## Where the magic stops

The boundaries, stated as plainly as the wins:

- **Byte-source pipelines are `map`/`filter` only (v1).** `zip`, `flatMap`, `take`, `drop`,
  `scan`, the adjacent-grouping family: all compile errors on a decomposed source. The engine
  guards this at the one place that knows the stage list, so a decoder never has to.
- **Records are flat case classes** with `Int`/`Long`/`Double`/`String` fields. Nested records,
  options, collections in fields: not in v1, and the error says so at compile time.
- **One frame at a time.** The driver sees a single complete record; there is no lookahead and no
  cross-record window on a byte source.
- **Synchronous.** The emitted code is a `while` loop in a `try`/`finally`; there is no async
  variant.
- **A performance cliff to know:** `topN`, `reduce` and `extremumByElem` keep whole elements, so on
  a byte source they force every field live and rebuild the record per surviving element,
  projection pushdown is off. `sum`/`fold`/`count`/`avg`/`agg` and the key-projecting extremums
  decode only what they touch. The plan string makes this visible (`rebuildsRecord=true`).
