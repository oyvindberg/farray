<p className="lede">
  Sometimes you don't have the elements up front — you push them one at a time and want an{" "}
  <code>FArray</code> at the end. That's what a <em>builder</em> is for, and it's the one place the
  standard-library abstraction actively works against a primitive-first library: reusing{" "}
  <code>scala.collection.mutable.Builder</code> would box every primitive at the interface. So FArray
  has its own — <code>FBuilder[A]</code> — and it turns out to beat even the specialized unboxed
  <code>int[]</code> builder from the standard library.
</p>

## Why the standard builder boxes

`Builder[A, To]` has one append entry point: `def addOne(elem: A): this.type`. `A` is an ordinary
erased type parameter, so at the bytecode level the descriptor is `addOne(Object)`. There is no
`addOne(int)` — there can't be, the trait is generic. So when you write `b += anInt`, the compiler
must box the `int` to an `Integer` **before the call**, because the callee only accepts a reference:

```
b += 42
  ⇓  Integer.valueOf(42)      // allocation, at the call boundary
  ⇓  b.addOne(theInteger)     // box already made — the builder can't undo it
```

Specialized builders like `ArrayBuilder.ofInt` store a real `int[]` internally — but they still
inherit `addOne(Object)` from the trait, so held at the trait's static type (which is how any generic
code holds them), every append still round-trips through a box and an unbox. The only escape is to
hold the *concrete* `ArrayBuilder.ofInt` type so the overloaded `addOne(Int)` is picked statically —
brittle, and impossible through a generic signature.

## The design: the map trick, for appends

FArray already solved unboxed element handling for `map`/`foldLeft`: the surface op is `inline`, the
element kind is resolved at the concrete call site via `summonFrom` on `${K}Repr[A]`, and the
primitive flows through a per-kind array. `FBuilder` reuses it verbatim. `FBuilder[A]` is an opaque
type over a generated `FBuilderBase`, whose concrete subclasses are the same per-kind `${K}Group`
growable buffers already backing `groupBy`/`collect`. Only the hot append is kind-dispatched:

```scala
inline def += (elem: A): FBuilder[A] = { builderAddImpl[A](b, elem); b }
//                                        summonFrom[${K}Repr[A]] → IntGroup → store an int
```

Every other method (`++=`, `sizeHint`, `clear`, `result`) is a plain virtual call on the base — none
of them touch a primitive element type, so none can box. `result()` hands the internal buffer to a
leaf under the house slack rules — no defensive copy — and `clear()` keeps the array for cheap reuse.

## The API

```scala
val b = FArray.newBuilder[Int]   // element kind resolved HERE, at this call site
b += 1                     // inline, UNBOXED: an int straight into an int[]
b += 2
b ++= FArray(3, 4, 5)      // bulk: leaves arraycopy'd, trees materialized once
b.sizeHint(1024)           // pre-grow the backing array
val fa = b.result()        // slack-wrap into a leaf, no defensive copy
b.clear()                  // reset to empty, keep the array
```

Plus `addOne`/`addAll` aliases, `length`/`knownSize`/`isEmpty`/`nonEmpty`, and — for stdlib interop —
`b.asScala`, a real `mutable.Builder[A, FArray[A]]` for `Factory`/`to(...)`. That adapter is
deliberately **second-class**: it's the boxing path, there so generic collection code *can* target
FArray, not the path you reach for when you care about speed.

## Beating the specialized int[] builder

Every builder here grows from nothing — none is told the size up front, which is the whole reason you
reach for a builder. So this is a fair fight, and it isolates the one thing that differs: how the
append crosses the type boundary. Note two rivals in particular — scala's `ArrayBuilder`, held at its
trait type (the way generic code holds it), boxes every `int` through `addOne(Object)`; zio's
`ChunkBuilder.Int`, held at its *concrete* type, is genuinely unboxed. FBuilder beats both.

## Use sizeHint when you can

If you do know the count — even roughly — `sizeHint(n)` pre-allocates the backing array once instead
of growing it through doublings from 16, and it measures at **≈2× the builder's own unsized
throughput** at scale. That's a self-relative number, not a fresh win over the field: every rival
builder has `sizeHint` too and speeds up the same way, which is exactly why the chart above keeps
everyone unsized. Hinting just lands FArray closer to the `tabulate` known-N ceiling; reach for it
when you can, and when you can't, the doubling growth is the standard amortized-O(1) append.

Two honest edges: `result()` hands back the *shared* buffer — the contract is result-then-stop (or
`clear()` and rebuild), not keep-appending — and tiny reference builds (≈10 elements) are the one
spot a warm `ArrayBuffer` edges you.
