  </li>

That last point is a consequence of how `inline` works here. `mapImpl` is `inline`, so the dispatch
and your lambda are resolved and lifted at the call site; `mapLeafIntInt` is not, so the
one heavy loop is compiled a single time and shared. The price of crossing that hand-off is that the
lambda has to become a function value, hence the SAM. But it's a *specialized* SAM, so nothing boxes,
and it's one allocation per `map` call, not per element; the JIT inlines its `apply` into the shared
loop at runtime. In the bytecode it's a single `anonfun` lifted by one `invokedynamic`, emitted once,
not twice.

The version that splices your lambda straight into the `while` loop, with no SAM at all, is `.fuse`,
which is why [fusion](../fusion/index.mdx) is a separate gear. What the inline layer buys on
its own is narrower but still decisive. A generic `map[B](f: A => B)` compiles once, generically, and
leans on the JIT to inline and specialize it afresh at each call site. That holds until several
distinct lambdas make the site megamorphic, at which point the JIT gives up and the loop turns
generic and virtual-dispatched (and, for element types it can't specialize, boxing on top). FArray
never writes that method down: the specialization is in the call site from compile time, so it holds
however large the surrounding method grows.

String. On its own, `map` is no rout:

## Where it stops being a tie

Measured against a bare array, those two charts are a wash: a few percent shy on
`Int`, a dead tie on `String`. That's the texture of a *micro*-benchmark: one operation over one
array, in isolation, where a lone `Array.map` (the one shared generic map Scala's standard library
bolts onto raw arrays) is a call the JIT already inlines fully and the
opaque wrapper plus the specialized SAM are pure overhead it doesn't carry. FArray isn't built to win
those by a percent. It's built for what happens once the benchmark stops being a micro-benchmark,
and it doesn't take much.

Write eight of that very same `map`, with eight *distinct* lambdas, in one method — the profile any
nontrivial method builds up. On `Int` at 100k, IArray drops to a third of FArray's speed. First,
what that is *not*: boxing. The allocation profiler shows IArray and FArray allocating byte-for-byte
the same here, eight `int[]` per call, because an `Int => Int` lambda is specialized
(`apply$mcII$sp`) and boxes nothing even when the map isn't inlined. The gap is pure compute.

IArray funnels all eight lambdas through its one shared `Array.map`, and that call site now sees
eight different `Function1` (Scala's lambda interface) classes, past the JIT's ≥3-type megamorphic
threshold, so it can no longer inline the map. Instead of the eight tight, inlined `int[]` loops it
would have produced, every element runs through one generic, unspecialized loop with a real virtual
`apply`. On trivial `Int` work (`_ + 1`) that per-element overhead is the entire cost, so it shows
as a multiple; on `String`, where each element already does real allocating work, the same overhead
is a rounding error — which is the tell that the cost is dispatch, not allocation. It ties through 1k
because small inputs stay near the fixed per-call costs; the penalty only takes over once there are
enough elements to feel it.

FArray has no shared site to poison: each lambda was already bound to its own specialized loop at
compile time, so eight maps are eight tight `int[]` loops, however many of them you write.

One sibling deserves a name here: `mapConserve`, the identity-preserving map used by compilers and
transformers (`if (f(x) eq x)` for every element, return `this`). FArray's version keeps
the reference-reuse semantics and the specialized loop, and returns the *original* array untouched
when nothing changed: no allocation at all on the no-op pass.
