## The tax, and where it isn't

A `PartialFunction[A, B]` (Scala's reification of a pattern match: a lambda paired with an
`isDefinedAt` test) is a generic runtime object, and a collect loop consults it per element:
the good implementations (fs2 and zio, the two streaming libraries) via one `applyOrElse` call
with a sentinel default, the standard library via `isDefinedAt` + `apply`. Generic means erased: on `Int` elements every question and
answer crosses through `Integer`. That tax has nothing to do with *arrays*:
our first implementation had unboxed storage on both sides of the PF boundary and still ran at
**0.65×** of the best rival at 100k Int. The boundary itself was the whole cost.

The call site, though, contains a pattern-match *literal*, and a literal is
compile-time information:

```scala
xs.collect { case x if x % 2 == 0 => x * 2 }
```

`collect` is an inline op, so a small macro (code that runs inside the compiler and rewrites the
typed syntax tree) sees that literal and splits it: the pattern and guard
become a predicate `x => x % 2 == 0`, the case body becomes a transform `x => x * 2`, and both feed
a one-pass impl exactly the way <Link to="/operations/filter">filter's</Link> and{" "}
<Link to="/operations/map">map's</Link> lambdas do: `inline` parameters, spliced into the
per-element loop, unboxed end to end, with the output written filter-style into one max-size array
(slack-wrapped, no growable buffer, no trim copy). No `PartialFunction` is ever constructed. For a
single simple case there isn't even a match in the output: the guard *is* the branch, evaluated
once per element.

The fine print:

<ul className="points">
  <li>
    <strong>Destructuring and multi-case matches</strong> split into two mirrored matches (one
    answering yes/no, one producing the value), with the pattern binders hygienically freshened.
    Patterns and guards may then evaluate more than once per element (the usual purity assumption).
  </li>
  <li>
    <strong>A stored PF</strong> (<code>val pf: PartialFunction[…]</code> passed by name) can't be
    picked apart; it falls back to the runtime path unchanged.
  </li>
  <li>
    <strong>Every element kind is carried</strong>: the split lambdas ride the same per-kind
    dispatch as filter/map, so <code>Float</code>/<code>Byte</code>/<code>Char</code> collections
    get the same treatment as <code>Int</code> and refs.
  </li>
</ul>

## We're here for the crushes

A lone collect is the friendliest case a rival will ever see: one call site, one `PartialFunction`
class, and the JIT devirtualizes and inlines the whole consultation. Real methods aren't like that.
With eight distinct pattern matches through `collect` in one method (a parser, a router, any
dispatch-heavy code), every rival funnels eight PF classes through its one shared collect loop:
the `applyOrElse` site goes megamorphic, stops inlining, and on primitives re-boxes every element.
FArray's collect has no shared site to poison; the macro gave each call site its own loop at
compile time:
