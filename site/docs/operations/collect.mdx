## The tax, and where it isn't

A `PartialFunction[A, B]` is a generic runtime object with two entry points, and a collect loop
exercises it per element: ask (`isDefinedAt`), then transform (`apply`). Generic means erased — on
`Int` elements every question and every answer crosses through `Integer`, and the guard logic runs
twice. Here's the honest part: that tax has nothing to do with *arrays*. Our first implementation
had unboxed storage on both sides of the PF boundary and still ran at **0.65×** of the best rival at
100k Int — the boundary itself was the whole cost.

But you didn't write an object with two entry points. You wrote a pattern match — a *literal* — and
a literal is compile-time information:

```scala
xs.collect { case x if x % 2 == 0 => x * 2 }
```

`collect` is an inline op, so a small macro sees that literal and splits it: the pattern and guard
become a predicate `x => x % 2 == 0`, the case body becomes a transform `x => x * 2`, and both feed
a one-pass impl exactly the way <Link to="/operations/filter">filter's</Link> and{" "}
<Link to="/operations/map">map's</Link> lambdas do — `inline` parameters, spliced into the
per-element loop, unboxed end to end. No `PartialFunction` is ever constructed. For a single simple
case there isn't even a match in the output: the guard *is* the branch, evaluated once per element.

The fine print, stated plainly:

<ul className="points">
  <li>
    <strong>Destructuring and multi-case matches</strong> split into two mirrored matches (one
    answering yes/no, one producing the value), with the pattern binders hygienically freshened.
    Patterns and guards may then evaluate more than once per element — the usual purity assumption,
    same as everywhere else on this site.
  </li>
  <li>
    <strong>A stored PF</strong> (<code>val pf: PartialFunction[…]</code> passed by name) can't be
    picked apart — it falls back to the runtime path unchanged.
  </li>
  <li>
    <strong>Every element kind is carried</strong> — the split lambdas ride the same per-kind
    dispatch as filter/map, so <code>Float</code>/<code>Byte</code>/<code>Char</code> collections
    get the same treatment as <code>Int</code> and refs.
  </li>
</ul>
