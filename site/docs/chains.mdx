Three effects compound down a chain:

<ul className="points">
  <li>
    <strong>Boxing is paid per stage.</strong> A three-stage pipeline over boxed elements boxes at
    every crossing; chaining multiplies the tax rather than amortizing it. FArray's stages hand
    each other primitive arrays.
  </li>
  <li>
    <strong>Structural stages cost nothing.</strong> A <code>take</code>, <code>drop</code> or{" "}
    <code>reverse</code> in the middle of a chain is an O(1) lazy node for FArray and a full copy for
    every array-backed rival, a copy of data whose only purpose is to be consumed by the next stage.
  </li>
  <li>
    <strong>Big methods slow the rivals down.</strong> The array-backed collections run every lambda
    you pass to <code>map</code>/<code>filter</code> through one shared, generic copy of that method.
    Pack several different lambdas into one method and the JIT can no longer keep that shared copy
    specialized, so it deoptimizes and slows down. FArray compiles each lambda into its own loop, so
    there is nothing shared to spoil. This is what turns a one-line benchmark tie into a loss in real
    code, shown in full <Link to="#the-method-size-effect-eight-distinct-maps">further down</Link>.
  </li>
</ul>

## The method-size effect: eight distinct maps

This chain exposes the shared-call-site problem: eight *different* lambdas through `map` in one
method, the profile any nontrivial method builds up.

💣 **A landmine hides in the primitive case.** Watch IArray on `Int` (left chart below): dead even
with FArray through 1k, then it drops to a *third* of FArray's speed at 10k and never recovers. The
same code, one input-size step, a 3× loss from nowhere.

<details>
<summary>Why it detonates, and only at scale</summary>

**What:** the same eight-map method, run at one size larger, loses 3× against the identical FArray
code, with no source change of any kind.

**How:** IArray funnels all eight lambdas into its one shared `Array.map`. That call site now sees
eight `Function1` (Scala's lambda interface) classes, past the JIT's ≥3-type megamorphic threshold,
so it stops inlining them and, on `Int`, re-boxes through `Integer` at every stage boundary. Those
boxed `Integer[]` intermediates fit in cache up to ~1k elements, which is why it ties there, but they
are far heavier than FArray's `int[]`, and the moment they spill the cache the re-boxing becomes pure
memory traffic. The loss is latent in any hot method and only surfaces once the data outgrows the
cache.

FArray has no shared site to poison: each lambda is bound to its own compiled loop, so eight maps are
eight tight `int[]` loops. On `String` there is no boxing to re-pay, so the field stays close, which
pins the mechanism as megamorphic *boxing*, not dispatch alone.

</details>

## A long interleaved structural chain

The last chain alternates `+:`, `:+`, `++` (prepend, append, concat) and
`reverse`, forced by one final `map`. For FArray that's a string of O(1) nodes and a single O(n)
traversal; for array-copying structures it's a full copy *per op*:
