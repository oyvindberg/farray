## Ten years of waiting for the JVM

<p className="lede">
  Scala collections read the way code should read, and the price is a heap allocation for every
  <code>Int</code> that passes through them. The <code>while</code> loop that avoids the boxing is
  miserable to write and worse to maintain. I spent about a decade waiting for something in
  between: specialization, miniboxing, the Dotty linker, Valhalla's <code>List&lt;int&gt;</code>. None of it shipped.
  So the conclusion, every release, was the same: if it has to be fast, write it in Java.
</p>

In 2023 I wrote a prototype out of spite: the whole collections API as `inline` `while` loops over
one flat `Array[AnyRef]`. It beat the collection library, but it boxed, and unboxing turned out not
to be something you bolt on. It needed per-kind storage, a core the inliner can't defeat, and a way
to keep a user's lambda unboxed across the library boundary. That was years of evenings I didn't
have, and the repo sat untouched for three years.

## And then, all at once

I picked it up again in June 2026, with Claude doing the heavy lifting. Seventeen days and nearly four
hundred commits later, all of it existed:

At 100k elements: **36× the fastest competitor**, **83× List**, and **15× the same pipeline run
eagerly on FArray itself**.

The reason is simple. Run those stages eagerly and each one allocates a collection whose only
purpose is to be consumed by the next. `.fuse` builds none of them:

<FusionDiagram />

It's a macro. At compile time the whole chain becomes one `while` loop, with no intermediate
collections, no `Function1`, and no boxing. The lowering is checked into the repo as a golden test,

## Three speeds

A single benchmark number doesn't mean much on its own, so here is the context for it. Fast JVM
code was never the hard part; anyone can write a `while` loop over an `int[]`, and nothing on this
site beats that. The hard part is getting that speed from immutable, expression-oriented code, where
erasure boxes your primitives and every pipeline stage materializes a collection that lives for one
line. The chart above is really three speeds:

<Ladder />

**Today's speed.** `List` and `Vector` pay a box, an allocation and a virtual call per element, per
stage. The Chunks keep arrays underneath but box at the stage boundaries. `IArray` doesn't box at
all, but it copies the whole array at each of the thirteen seams, and the copies are what you end up
paying for. They are all really allocated; escape analysis doesn't remove intermediates at this
depth.

**The type swap.** The same code with `FArray` under it. Storage is a real `int[]`, structural steps
like `take` and `reverse` are O(1) nodes instead of copies, and every lambda-taking op is `inline`,
which puts the unboxing in the method signature. That last part matters: the rivals that tie us on a
single op lose that tie as the surrounding method grows, because their unboxing depends on the JIT's
inlining budget and ours doesn't. No fusion involved, and it already beats the field.
[The next page](./chains.mdx) scores every chained benchmark in the suite.

**The word.** Views, iterators and LazyList attempt this at runtime and mostly add interpreter
overhead. `.fuse` does it at compile time, and what it emits is the `while` loop you would have
written by hand. You just don't have to write it, or maintain it.

In practice you swap the type everywhere and add `.fuse` on the paths that matter. The rest of the
site explains each layer.
